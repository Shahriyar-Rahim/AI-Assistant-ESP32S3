# Distributed Edge AI Assistant

This workspace contains an in-progress ESP32-S3 distributed assistant. The firmware targets ESP32-S3 N16R8 and builds independent I2S peripherals for INMP441 input and MAX98357A output. It includes WPA2 setup, NVS credential storage, authenticated TLS WebSocket PCM transport, reconnect with bounded replay/ACK/NACK, playback, and persistent microphone/backlight controls. Firmware OTA downloads the authenticated image over HTTPS, verifies SHA-256 before switching dual OTA slots, and enables boot rollback. The display driver automatically selects an SSD1306 OLED at I²C address 0x3C/0x3D when detected on GPIO1/2, or falls back to the ST7735 TFT on SPI2. The ST7735 uses a 160×128 landscape layout, an LVGL face-only idle/interaction view and dashboard widgets; OLED and games are not yet LVGL widgets, and the complete wizard is unfinished. The FastAPI backend includes the voice pipeline, typed actions, calendar/games/integrations, automation rules, telemetry, display configuration, and OTA management; React supplies monitoring, display, OTA, alarm, settings, and developer surfaces. The simulator remains explicitly `SIMULATED`. USB validation confirms firmware boot, microphone samples, automatic ST7735 selection and a backend WebSocket connection on the local LAN. Display appearance, audible speech, wake recognition, sustained streaming, and physical OTA remain unverified.

## Local backend

1. Install Python 3.11 or newer.
2. `python -m venv .venv && . .venv/bin/activate`
3. `pip install -r backend/requirements.txt`; for wake-word detection install `pip install -r backend/requirements-wakeword.txt`. Install `espeak-ng` on native Linux hosts for local TTS; the backend container installs it automatically.
4. `cp .env.example .env`, set distinct random `DEVICE_TOKEN` and `SIMULATOR_TOKEN`, set a 32+ character `AUTH_SIGNING_SECRET`, and configure a strong `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_PASSWORD`.
5. `cd backend && ../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload`
6. Visit `http://localhost:8000/docs` or `http://localhost:8000/api/v1/health`.

Starting Uvicorn from `backend/` lets relative model paths such as `./app/models/hey_buddy.onnx` resolve correctly; python-dotenv finds the root `.env`. The audio WebSocket requires the configured shared device token or a separately issued per-device token and a registered device hello message. Dashboard routes require bearer authentication. By default, device audio is processed in memory only. If the user explicitly enables Personalization in the dashboard, verified voice PCM and transcripts are encrypted with `VOICE_ENCRYPTION_KEY`, retained for at most 30 days, and removable from that page; the derived language/response-length profile is used only for that user's replies. Production integrations that store credentials require a generated `INTEGRATION_ENCRYPTION_KEY`; voice enrollment and encrypted personalization require `VOICE_ENCRYPTION_KEY`.

The device's saved backend URL must point to the PC's current LAN address and port, and that hostname or IP must also be listed in `ALLOWED_HOSTS`. Reserve a DHCP address or use a stable local hostname to avoid breakage when the address changes. The device settings page provides a 0–100% speaker volume control; an administrator may also say “set volume to 50 percent.” The value is persisted and replayed on reconnect, but a successful send is not a hardware acknowledgement. Firmware containing the control must be flashed to the device.

For a connection timeout, first verify the backend is running and `curl http://<PC-LAN-IP>:8000/api/v1/health` succeeds on the PC. Check the device's station IP in its serial log, then run `ping -c 3 <device-IP>` and `ip neigh show <device-IP>` on the PC. An `INCOMPLETE` or `FAILED` neighbor entry means the PC could not resolve the device's link-layer address; check router/AP client isolation, guest network policies, both devices' Wi-Fi association, and network equipment before troubleshooting WebSocket authentication. A firewall can also prevent TCP access once link-layer reachability is working. Do not expose port 8000 to public networks for this check.

Run the dashboard in another terminal with `cd dashboard && npm install && npm run dev`, then open `http://localhost:5173`. The authenticated dashboard includes device, calendar/reminder/to-do/alarm, game, AI/voice, audit/export, integration, weather, endpoint-monitoring, live telemetry, display configuration, OTA release, device settings, and developer diagnostics workflows. Display Studio can send live pages and weather coordinates to a registered device; the display also accepts voice page commands. Remaining limitations are tracked in the implementation ledger.

For local AI fallback, run Ollama on the PC, install an appropriate model, and set `OLLAMA_FALLBACK_MODEL` to its exact name and `OLLAMA_BASE_URL` to the server URL. When the configured cloud provider fails, voice requests try that local model; a running server, installed model and enough RAM are required. No local model is installed automatically. This fallback does not make the ESP32 independent of the PC or network.

Voice commands such as “make a to-do for shopping list” create a named list and prompt for items. Each item is stored as a separate task, visible and completable in the dashboard. “Take a note” prompts for its content. These follow-up conversations expire after two minutes; saved lists, tasks and notes remain in the database.

For calendar entries, “schedule a meeting called Dentist tomorrow” asks for the missing time; a reply such as “at 7 AM” saves a calendar event, not a reminder or an alarm. The local scheduler supports times today or tomorrow and relative durations; unsupported weekday and explicit date phrasing is rejected rather than guessed. Existing incorrectly dated entries are not automatically changed. Voice-created task pages and notes shown during these flows are filtered to the requesting user and shared entries; other display entry points retain their existing behavior.

Voice timers support “set a timer for 5 minutes”, “how much time is left on my timer”, and “cancel my timer”. Durations are whole seconds, minutes or hours between 10 seconds and 7 days; other phrasing is not yet supported. Timers are stored separately from calendar events as timer-kind schedule records. If several timers are active, voice cancellation asks you to delete the intended record from the calendar dashboard instead of guessing. “Set an alarm” asks for a time and listens for the reply. A schedule is sent immediately to a connected device advertising local scheduling, but sending is not an acknowledgement that it was stored or will sound. Delivery, device clock validity, power, and audio output remain necessary; the existing firmware plays alerts sequentially, so simultaneous alerts can be delayed. Device sync retains already-due pending items briefly to avoid losing an alarm in a sync race, so cancelling at or after its due time cannot reliably stop that alert.

Private facts may be taught explicitly, for example “remember that my home is near the park,” recalled with a related personal question, and removed with “forget my home” or “forget everything.” These facts are stored encrypted in the backend database under the verified user, using `VOICE_ENCRYPTION_KEY`; voice enrollment and successful speaker verification are required even in onboarding mode. Keep a secure backup of that key: changing or losing it makes existing facts unreadable. Facts are not an automatic import of PC files or contacts. The assistant does not accept passwords, API keys or payment secrets as taught facts. Existing legacy learned facts and optional voice-interaction retention have separate storage and privacy behavior.

An optional semantic fallback can help recall paraphrases after keyword matching fails. Install a local GGUF Ollama model, disable Ollama cloud features with `OLLAMA_NO_CLOUD=1` in the **Ollama server's** environment (or `disable_ollama_cloud` in its server configuration), restart Ollama, then set `PRIVATE_MEMORY_MODEL` to the installed model name and restart the backend. `PRIVATE_MEMORY_OLLAMA_URL` defaults to `http://127.0.0.1:11434`; only numeric loopback URLs are accepted. Before sending facts, the backend checks the model details and refuses reported remote models and non-GGUF models. Use a trusted local Ollama server with cloud features disabled: a loopback address and model inspection cannot independently prove what another process does with requests. Decrypted facts are sent to that local process in memory. With Mem0 disabled, the fallback handles up to 100 facts per user; it returns only a saved fact selected by the model and may still select the wrong fact or fail to understand a question. It does not perform semantic deletion or unrestricted understanding. With no model configured the existing keyword behavior remains unchanged.

Mem0 semantic search can be enabled by installing `backend/requirements-mem0.txt`, setting `MEM0_ENABLED=true`, `PRIVATE_MEMORY_MODEL` to an installed local chat model, `MEM0_EMBEDDING_MODEL=all-minilm`, and `MEM0_EMBEDDING_DIMENSIONS=384`, then restarting the backend. Install both models on Ollama first; for example, `ollama pull qwen2.5:0.5b` and `ollama pull all-minilm`. Ollama must run on numeric loopback with cloud disabled. Mem0's telemetry is disabled before loading the SDK. It builds a temporary Qdrant index and history database in RAM from the verified user's encrypted private facts for each eligible recall; the encrypted backend database remains the durable store and deleting a fact removes it from future indexes. No Mem0 vector or history data is deliberately persisted, although operating-system swap, crash dumps and Ollama's process memory may contain plaintext. Rebuilding the index on every search trades speed for avoiding an additional plaintext database; it is capped at 200 facts. Only recognized personal questions use this path; the local model still selects an existing fact, not a generated answer. It can miss or select the wrong fact, and does not provide automatic learning, semantic deletion, or unrestricted understanding. Voice verification and explicit teaching remain required.

Before enabling it, check the installed models with synthetic facts: from `backend/`, run `RUN_LOCAL_MEM0_TEST=1 LOCAL_MEM0_CHAT_MODEL=<chat-model> .venv/bin/python -m pytest -q tests/test_mem0_index.py::test_local_ollama_and_mem0_with_encrypted_facts`. This requires Ollama on `127.0.0.1:11434` and the `all-minilm` embedding model; it does not guarantee accuracy for other questions. The `smollm2:135m-instruct-q4_K_M` model failed this check by returning the wrong JSON shape and should not be used for this feature. Choose a capable local model and ensure sufficient available memory before enabling it.

For Docker, set those variables in `.env`, start with `docker compose --profile memory up -d --build`, then run `docker compose --profile memory exec ollama ollama pull qwen2.5:0.5b` and `docker compose --profile memory exec ollama ollama pull all-minilm`. The optional Ollama container shares the backend network namespace so the backend reaches it through loopback; cloud is disabled and models persist in the `ollama_models` volume. The first pulls require internet and disk space; subsequent inference is local. Restart the backend after changing settings. This profile requires a running Docker daemon and sufficient memory. The small example model prioritizes resource use, not accuracy.

A microSD card supplies storage, not extra RAM or processing power. It does not by itself make an incompatible USB camera streamable, route frames to the backend, or run Whisper on the ESP32-S3; those require compatible drivers, sufficient working memory and compute, an implemented transport and appropriate model support. Local Whisper can instead run on the PC without internet, provided the model and dependencies are installed and the ESP32 can connect to that PC.

On a connected physical device, “roll a die”, “spin the roulette wheel” and “choose a decision symbol” start persistent on-device utilities; say “again” or the corresponding action for another turn, and “stop” to leave. Roulette uses the single-zero European wheel. The random choices are device-generated, but speech recognition and speech output still require the local backend and a working network connection.

“Remember my face” starts a 60-second background enrollment on the configured camera source. Stay alone in view: the assistant collects single-face samples and reports success only if enough mutually consistent samples are captured. Enrollment status is visible on the Camera & memory page. Face recognition is probabilistic and is not proof of identity or liveness. If an unknown entry is the same person as an existing identity, explicitly select both on that page and confirm the merge; embeddings and event references are retained, but the removed identity cannot be restored automatically. No face is merged based solely on a recognition guess.

Optional local hand-gesture recognition uses the [MediaPipe Gesture Recognizer](https://ai.google.dev/edge/mediapipe/solutions/vision/gesture_recognizer). Install `backend/requirements-gestures.txt` in a compatible backend environment, obtain the [official model bundle](https://storage.googleapis.com/mediapipe-models/gesture_recognizer/gesture_recognizer/float16/1/gesture_recognizer.task), set `GESTURE_MODEL_PATH` to its local path and `GESTURE_ENABLED=true`, then restart the backend. `CAMERA_ENABLED=true` and an enrolled owner face are also required. A single recognized owner face and three consecutive matching detections are required: thumbs-up, victory and open palm request happy, excited and curious expressions on connected devices. Recognition is probabilistic; the hand is not associated securely with the detected face, and gesture actions do not authorize sensitive operations. Multiple faces, missing frames and unknown faces reset the gesture gate. The recognition package and model must be installed locally; the existing backend environment is not modified automatically.

For the local container stack, configure the environment as above, then run `docker compose up --build`. It serves the backend at `http://localhost:8000` and dashboard at `http://localhost:8080`.

## Firmware

Firmware uses PlatformIO with the ESP-IDF framework. From `firmware/`, run `pio run`. The custom PlatformIO board target is ESP32-S3 N16R8 with 16 MB flash and 8 MB OPI PSRAM. At boot firmware plays a two-second speaker test tone through the MAX98357A on I2S1, pausing and then resuming microphone capture. To flash a connected board, use `pio run -d firmware -t upload --upload-port /dev/ttyACM0` and replace the port as needed. The current firmware was flashed and verified over USB; logs confirm I2S initialization, microphone samples, and ST7735 selection. Audio uplink still reports queue overflow and intermittent WebSocket write timeouts, and audible speaker output/wake recognition have not been confirmed. Verify the actual board variant and attached display module before flashing. GPIO and peripheral assignments are centralized in `firmware/include/hardware_config.h`.

Physical wiring and electrical characteristics must be checked before powering attached modules. The TFT's positive `LED` backlight input may use GPIO13 PWM directly only if the module's current limiting keeps the pin within ESP32-S3 limits; see the backlight wiring notes in [`docs/hardware.md`](./docs/hardware.md).

See [`docs/hardware.md`](./docs/hardware.md) for the complete pin wiring and power-on checklist and [`docs/deployment.md`](./docs/deployment.md) for local and hosted deployment limitations.
External service setup and credential requirements are listed in [`docs/external-dependencies.md`](./docs/external-dependencies.md).

## Simulator

After starting the backend, set `BACKEND_URL`, `DEVICE_ID`, and `SIMULATOR_TOKEN` in the shell and run `python simulator/device_simulator.py`. `--scenario replay-gap` verifies server NACK/ordered-replay ACK behavior, `--scenario reconnect` exercises two simulated sessions, `--scenario observe` waits for server control events (optionally filtered by comma-separated `SIMULATOR_EXPECT`), and `--scenario pcm --pcm-file capture.pcm` streams an explicitly supplied raw 16 kHz mono PCM16 fixture. All simulator output is marked `SIMULATED`; synthetic traffic or a supplied recording is not evidence of physical hardware, speaker verification, anti-spoof model accuracy, provider availability, or OTA rollback on the ESP32.
